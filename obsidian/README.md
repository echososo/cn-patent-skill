# Obsidian 案件图谱与检索轨迹图谱

这个目录有两张图，各管一件事：

| 图 | 回答什么 | 脚本 |
|---|---|---|
| 案件图谱 | 这件案子站不站得住：哪条权项没证据、哪条被致命问题指着 | `build_case_graph.py` |
| 检索轨迹图谱 | 这条路是怎么走出来的：查过什么、比过什么、候选怎么被打掉或升成核心、还有什么没查完 | `build_search_trail.py` |

两个脚本各认各的标记，可以并存在同一个 `图谱/` 下；都是纯 Python 标准库，不联网、不装依赖。

## 案件图谱

把一件案子的申请文件、证据矩阵、模拟审查报告连成一张图：
每条权利要求连着它的区别特征、支撑证据、命中它的对比文件、指向它的审查问题。
一眼看出哪条权项没证据、哪条被致命问题指着——这件案子站不站得住，图上直接看。

### 用法（三步）

1. 让 agent 按本技能跑完审查/矩阵（输出的表格格式就是脚本认的格式），材料都在一个案件文件夹里；
2. 跑：

   ```
   python3 obsidian/build_case_graph.py <案件文件夹>
   ```

3. 用 Obsidian 打开案件文件夹（或它所在的库），点 `图谱/案件_图谱.canvas`。
   没装 Obsidian 也能直接读 `图谱/` 里的 markdown，从 `案件总览.md` 点进去。

先看效果：包里演练案例已经带了一张现成的图——`examples/demo-case/图谱/案件_图谱.canvas`。

### 它认什么材料

| 图上的东西 | 从哪来 | 格式要求 |
|---|---|---|
| 权利要求 1..n（含引用关系） | 申请文件 | 「权利要求书」栏目下 `1.` `2.` 编号条目 |
| 区别特征 | 矩阵 1 | 表头含「特征编号」和「D1」 |
| 说明书支持、退守层级 | 矩阵 2 | 表头含「权项」和「说明书段落」 |
| 技术效果台账 | 矩阵 3 | 表头含「技术效果」和「因果链」 |
| 证据 SRC-XXX-000 | 矩阵 2、3 | 证据编号按 references 里的口径写 |
| 对比文件 D1..Dk | 矩阵和检索记录 | 检索记录里写一行「D1：文献号 标题」标题就能带上图 |
| 审查问题（前缀封闭集 OBJ/NOV/INV/SUP/CLR/CLM/EFF/FORM） | 模拟审查报告 | `### CLM-01` 这种块，字段用「- 严重程度：」这种列表 |

缺哪样就少画哪样，只有权利要求也能出图。

### 规矩

- 只读你的材料，生成的东西全在 `图谱/` 子文件夹里；
- 重跑会覆盖它自己生成的文件（文件头带 `generated-by: build_case_graph` 标记），
  你手写的笔记它不碰，但别把自己的笔记也放进 `图谱/`；
- 上一轮生成、这一轮已经不在的笔记会被清掉（并报出清了哪几个）。
  审查报告改问题编号时用得上：`INV-01` 改判成 `CLM-01` 之后，旧那份不会继续留在图上
  冒充一个真实存在的问题。判断依据仍是那个标记，手写笔记不受影响；
- 纯 Python 标准库，不联网、不装依赖。

## 检索轨迹图谱

案件图谱画的是结果，这张画的是过程。一件案子写到最后，往往查过几十篇文献、打掉好几个候选、
把某个从属特征升成核心，可交出去的申请文件里一个字都看不到。检索轨迹图谱把这些留下来，
给发明人、代理人或接手的人看：查过什么、比过什么、每一步为什么这么选、还有什么没查完。

### 用法（三步）

1. 让 agent 按 `references/search-trail.md` 的格式，在每轮检索结束时把本轮追加进案件目录的
   `检索轨迹台账.md`（候选、轮次、查询式、文献、对照五张固定列的表；词表封闭，写错会报错）；
2. 跑：

   ```
   python3 obsidian/build_search_trail.py <案件文件夹>
   ```

3. 双击 `图谱/检索轨迹/检索轨迹图谱.html`（任何浏览器，不联网）。里面两个视图：
   - **图谱视图**：知识图谱那种——节点能拖，滚轮缩放，点轮次收起／展开它查到的文献，
     收起后这一轮对候选的打击合并成一条带次数的虚线；候选的外圈颜色就是它的最终去向；
     右侧是地图式图例，点任何节点右侧换成它的来龙去脉；深浅色可切，「适应窗口」一键居中；
   - **流程视图**：四列从左到右——轮次 → 文献 → 候选 → 最终去向，适合打印；
   - 两个视图都有「导出 PNG」，发给不方便开网页的人；「上一轮／下一轮」按时间回放。
   只想看字的看 `检索轨迹总览.md`（“候选 × 轮次”演变表和每个候选从提出到定局的一条线）；
   Obsidian 用户从总览点双链进 `候选/`、`轮次/`、`文献/` 的笔记。不生成 `.canvas`：
   它只能在 Obsidian 里当库打开时看，给别人看不如 HTML 和 PNG。

先看效果：`examples/demo-case/图谱/检索轨迹/检索轨迹图谱.html`（虚构数据）。

### 图上怎么读

- 文献 → 候选的线按判定上色：红是新颖性层面被打掉（明文记载／毫无疑义确定／实测推翻），橙是创造性层面有威胁
  （部分接近／记载不清），绿是未记载或实测支持，蓝是教导相反——蓝线是答辩时最有用的，灰是人为取舍；
- 候选 → 最终去向：独权核心、从属权项、仅说明书、放弃、待定，交付前不该还有待定；
- 图谱视图里节点越大，说明它牵扯的对照越多：轮次按检出篇数，候选按被打的次数——这就是工作量本身；
- 网页是给外人看的：`线索未解决`、`无关` 这两个角色不外显，只进 `检索轨迹总览.md`；
- 「公知常识」「本案实验」「人为决策」各是一个专门的节点：靠常识打的判定、被自己实验推翻或坐实的候选、
  用户或代理师为篇幅砍掉的线，都在这里连到候选——为什么走这条路，往往一半是文献、一半是这三样。

### 规矩

- 只读台账，生成的东西全在 `图谱/检索轨迹/`；重跑覆盖自己生成的文件（标记 `generated-by: build_search_trail`），
  手写的不碰，上一轮生成、这一轮已不存在的会清掉并报出来；
- 台账里最终去向、类型、全文状态、最终角色、判定、影响六列只认词表里的词，
  遇到别的直接报错停下并列出允许值——不猜，猜出来的图对不上；
- 台账找不到或找到多份都会报错，可用 `--ledger` 指定；输出目录可用 `--out` 改。

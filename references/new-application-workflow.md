# 新案工作流

仅用于从零立项、挖掘并撰写一件新中国发明专利。旧稿优化、限定范围的评审和仅做格式修改不得套用本流程。

## 阶段 0：建立证据工作区

当用户要求完整推进新案时，建立独立案件工作区，名称可采用 `申请工作区-YYYYMMDD`。建议保留以下层次；已有项目结构足够清楚时不机械重建：

```text
00_来源快照/
01_实验方案/
02_参考实现/
03_测试/
04_实验结果与充分性评审/
05_申请文件/
```

- `00_来源快照` 记录代码、资料和版本来源，保持不可变。
- 对关键来源文件、代码快照和正式审查包记录版本号或 SHA-256，使实验、矩阵和终审能够绑定到同一精确版本。
- 需要验证新机制时，在 `02_参考实现` 或明确标记的工作副本中实现，不修改原项目和不可变快照。
- 记录运行环境、依赖、数据入口和一键复跑命令。涉及秘密或个人信息时，不复制无关数据。
- 在检索和对外发送材料前，按 [申请前风险](pre-filing-risk.md) 建立公开事件、优先权和保密风险清单；已公开内容可能影响新颖性时先报告，不假设存在宽限期。

## 阶段 1：锁定唯一主发明点

1. 阅读与本案有关的完整代码、测试、数据结构、接口契约和真实运行路径。用户材料很薄、代码残缺或根本没有代码时，把现有材料读完即可进入第 3 步；材料少只影响证据状态，不构成停下的理由。
   - 材料里的 `.docx` 和 `.pptx` 先转成 Markdown 再读：`python3 scripts/docx_to_md.py -i 文件.docx -o 文件.md`、`python3 scripts/pptx_to_md.py -i 文件.pptx -o 文件.md`。只扫 `.md` 和源码就说“材料读完了”是漏读——需求文档、架构评审和会议纪要经常只有 Word 或 PPT 一份。
   - 项目存在可用版本历史且历史与本案相关时，同时检查关键差异：被替换的常规方案、失败尝试、未合并机制和最终实现路径。每条结论记录提交号、文件位置和实际是否进入已发布版本；版本历史可帮助解释研发过程，但不能单独证明发明人身份、未公开状态或创造性。
2. 用至少一个真实问题做端到端走查：输入 → 中间表示 → 判断或路由 → 查询或执行 → 校验 → 输出。
3. 列出候选发明点。候选不限于用户材料里已实现的机制，至少从三个来源找：
   - 用户代码、数据和文档中已经做出来的机制；
   - 用户项目所在领域公认尚未解决好的技术问题——先列一张领域问题清单，标出哪些与用户给定的信息或代码有关联；
   - 我们自己能够给出完整技术方案解决的问题（拟议方案路线，可实施性按阶段 2 验证）。
   材料完成度不设门槛：代码有缺陷、项目在建、数据缺失，都不缩小这张清单。对每个候选逐一检查：
   - 技术问题是否真实存在，现有系统是否已经轻松解决；
   - 是否有明显更简单的常规方案；
   - 区别手段是否产生可解释、可验证的技术效果；
   - 是否只是普通模块拼接；
   - 是否能写出支持核心主张的实施例。
4. 从候选中选出最适合申请的一个作为唯一主发明点，标准是四问：初步检索后新颖性仍有空间吗；创造性支点能说清吗；技术效果能由机制推出或可验证吗；我们能写出完整可实施的方案吗（自行出方案补全也算能）。与用户材料关联度高是加分项，不是入选门槛。选定后形成两页以内的方案复述：真实问题、输入、关键中间状态、处理规则、输出、区别特征、技术效果和验证办法。
5. 围绕该方案至少完成 3 轮“方案修订 → 中英文检索 → 对照最接近专利和论文 → 再修订”。每轮记录日期、检索入口、查询式、关键文献及其影响，不用三次同义搜索充数。最接近现有技术优先按技术问题、用途和技术效果的关联性选择，不按共有词或共有特征数量机械决定。每轮结束时同步把本轮追加进 [检索轨迹台账](search-trail.md)：新提的候选、查过的入口和查询式、看过的文献、每篇文献打了哪个候选、判定是什么、候选因此怎么变。第 3 步列出的候选也要进台账（提出于 `R0`），后来被打掉的不删行。检索入口一个都打不开时，按检索与材料规范「一个入口都打不开时」处理：不停下来等，把稿子写完，新颖性和创造性只列待检索项，报告末尾附检索式清单。
6. 候选被证伪时回到第 3 步继续寻找，包括跳出用户材料、从领域问题清单重新取点；用户给定的方向本身泛泛或无创新时，不顺着硬写，而是向用户提出升级后的选题（说明它与原方向的关联和差距），或按下段给出不建议申请结论。

软件案件的检索按 [检索与材料规范](search-and-materials.md) 同时考虑专利、论文、标准、公开产品资料和开源实现。经过系统检索和候选回退后确实没有候选通过门槛时，应交付有证据的“不建议申请”结论，列明每个候选被哪份材料或哪项致命缺陷阻断；不得为了交稿制造弱发明点。

阶段 1 同步建立 [区别特征—创造性矩阵](claim-evidence-matrix.md)：逐项记录最接近现有技术、区别特征、该特征在本发明中的技术效果、实际解决的技术问题、第二文献或公知常识、是否给出技术启示，以及反对结合的理由。涉及 AI 或软件时，同时按 [AI 与软件专利](ai-software-patents.md) 核对技术问题—技术手段—技术效果链。

阶段 1 自评可靠后暂停，向用户提交唯一主发明点、两页内方案、关键证据和主要风险，等待确认。用户本次明确说“直接干到底”“无需阶段确认”或同义指令时，不暂停。

## 阶段 2：冻结实验方案并验证

写参考实现前先冻结实验方案，至少写明：

- 要验证的唯一技术主张；
- 可证伪假设；
- 对照基线和选择理由；
- 输入数据、边界条件与失败场景；
- 通过标准及其计算方法；
- 需要记录的原始结果和复跑命令。

随后完成最小但可运行的参考实现和测试。关键数字，例如状态转移数、搜索深度、窗口大小、覆盖率和对照结果，必须来自本次真实运行并可复算。参数只作为实施例时，说明选择依据，不宣称为“已验证默认值”。

参考实现证明的是可实施性，不等同于生产系统已经部署。失败结果如实保留；不得选择性隐藏会动摇主张的反例。拟议方案路线的案件，参考实现就是主要证据来源：验证通过后把相应条目从 `拟议待验证` 升级为 `参考实现支持`，再考虑写入核心权利要求；升不上去的留在从属项或删除。

把实验结果写入 [技术效果—证据矩阵](claim-evidence-matrix.md)，逐项标明基线、指标、原始结果、因果链、成立边界和证据位置。没有实验也能由技术逻辑直接推出的效果，要写明推导链；不能证明的效果从权利要求和确定性结论中删除或降格。

## 阶段 3：申请充分性评审

实验通过后、正式写申请文件前，按 [授权七道门](patentability-gates.md) 形成充分性评审：

- 核心技术问题和唯一主张；
- 最接近现有技术及逐特征对照；
- 审查员可能采用的文献组合和评价路径；
- 新颖性、创造性、客体、充分公开和支持风险；
- 实验是否实际证明了主张，未证明什么；
- 建议保留、下沉到从属项或放弃的特征。

充分性评审另做一次非法律性质的保护价值复核：当前可获得的权利要求是否容易被明显变体绕开、侵权特征能否从公开产品或可合法取得的运行证据中识别。该复核不替代授权七道门；如果每次为克服现有技术而缩窄后保护价值明显下降，必须向用户说明具体绕开方式和取证困难，不得只报“仍可能授权”。

每道门给出 `PASS`、`RISK`、`BLOCKED` 或 `N/A`，并附证据位置和最小补救。存在未处置的 `BLOCKED` 时不进入完整申请文件撰写；返回阶段 1 或 2，不用扩写掩盖缺陷。

## 阶段 4：撰写与交付

确认唯一主发明点后，按 [撰写与评审规范](drafting-and-review.md) 生成申请文件，并同步完成权项—支持矩阵和至少三级退守梯度。实施例数字应来自本案实验结果；引用数据时保留可追溯关系。

完整初稿形成后按 [模拟审查](examiner-simulation.md) 分轮执行：先运行平衡模拟实质审查，核实并修正致命和重要问题；再在修订稿上运行对抗式驳回压力测试；处理能够维持的攻击后，对受影响部分做平衡回归。形成“不修改答辩、最小修改、保守退守”三条路线后再做终审。两份提示词分开运行，不在方案阶段提前加载。申请文件完成后再生成技术交底书或其他阶段三材料，除非用户明确只要其中一种交付物。交底书按 [技术交底书模板](disclosure-template.md) 成文，附图走 mermaid 渲染链，末尾附证据状态一节。

终审记录最终文件的版本指纹。终审后发生任何实质修改，旧的审查通过状态失效，至少重跑受影响门槛、机械检查和全文一致性核对。

交付前把检索轨迹台账收口：每个候选的 `最终去向` 和每篇文献的 `最终角色` 填定，模拟审查阶段新查到的文献按一轮补进去，然后运行 `python3 obsidian/build_search_trail.py <案件目录>` 生成检索轨迹图谱，和申请文件、矩阵、审查报告一起列进交付物清单。没参与撰写的人靠这张图看出查过什么、打掉了什么、为什么最后走这条路。

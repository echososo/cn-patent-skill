# 检索与材料规范

用于现有技术检索、创造性评估、专利或论文全文收集，以及检索材料归档。

## 检索设计

1. 从拟保护的必要技术特征出发，拆出若干有检索意义的语义块：技术问题、对象、关键状态、处理动作、约束关系和技术效果；不要只搜发明名称，也不要把一整句中文作为唯一查询或把“系统、方法、智能”等泛词单独当核心检索词。
2. 同时设计中文和英文查询，覆盖同义词、上位词、实现术语和可能的跨领域表达。技术路线相近时可纳入其他应用领域，并记录哪些语义块用于扩展、哪些用于收窄。
3. 优先使用可追溯的专利数据库、官方来源、论文原文和标准原文。软件案件还应按公开时间和相关性核对产品文档、开源仓库及版本、工程博客或会议资料；不能因为它们不是专利就排除。Google Patents 等可作为入口，但关键结论应回到可读全文或可核验代码版本；具体走哪个入口按下文“检索入口”一节确定，不假定某个入口一定可达。
4. 新案阶段按 [新案工作流](new-application-workflow.md) 完成至少 3 轮真正改变方案或判断的检索闭环；其他任务按用户范围执行，不自设篇数配额。
5. 记录检索日期、实际用到的入口和打不开的入口、查询式、筛选标准和未覆盖范围，使“查过了”可以复核。中途换过入口的，记下在哪一步换的、原因是什么。这些写进本轮检索记录；新案还要按 [检索轨迹台账与图谱](search-trail.md) 把结论同步进台账，检索记录是正文，台账是索引，两者都要有。
6. 选择最接近现有技术时，优先考虑与本发明实际技术问题、用途或技术效果相关联的方案，再综合技术特征接近程度；不得只按标题、关键词或共有特征数量排序。
7. 将结果至少分为 `单篇可能覆盖`、`可能用于组合`、`需要取得全文`、`线索尚未解决`。被验证码、登录、失效链接或缺页阻断的线索必须留在最后一类，不能静默丢弃。

## 检索入口：能打开哪个用哪个，打不开就写明

检索什么都不用配置，也不需要任何 key。开工前先花几秒摸清这台机器此刻能打开哪些入口，然后按下面的顺序用，把实际用到的入口和打不开的入口一起写进检索记录。不要默认宿主一定能访问 Google 系：国内直连网络下 Google 搜索、Google Patents、Google Scholar 通常打不开。

**第一步，探测入口**（不用模型，几秒钟）：

```bash
python3 scripts/prior_art_search.py probe      # Windows：py -3 scripts/prior_art_search.py probe
```

它会列出 Google Patents、Espacenet、PATENTSCOPE、Lens、国知局公布公告、OpenAlex、arXiv、GitHub、Bing 各自通不通。把这张表连同日期抄进检索记录的「入口」一栏，之后按通的入口干活；本轮没必要重复探测。

**第二步，按顺序用入口**（前一条不可用或不够时再往下）：

| 顺序 | 入口 | 怎么用 | 说明 |
|---|---|---|---|
| 1 | 宿主里已经配好的专利检索类工具（任何名字） | 直接用 | 用户自己接了检索服务的情况；没有就跳过 |
| 2 | **国知局公布公告**（`prior_art_search.py cnipa`） | 查中文专利就先用它 | 官方库，国内直连就能用，给的是中文标题、中文摘要、IPC 和官方链接。要本机 Chrome/Edge 加 `pip3 install playwright`；两段式用法见下 |
| 3 | 包内 `scripts/prior_art_search.py` 其余子命令（免 key） | `patents`（Google Patents 检索）、`get`（一件专利的摘要、权利要求、说明书全文）、`papers`（OpenAlex + arXiv）、`code`（GitHub 仓库） | 结果是 Markdown，可直接进检索记录；用法见脚本开头 |
| 4 | 宿主自带的搜索与网页抓取 | 打开 Google Patents / Espacenet / PATENTSCOPE / Lens.org 的检索页和专利页；国内直连时用 Bing、百度学术查论文和产品资料 | 抓取工具常被反爬挡住，挡住了换下一个入口，别反复撞 |

### 国知局怎么查：分两轮

```bash
python3 scripts/prior_art_search.py cnipa 批任务调度 资源画像 异构算力      # 第一轮：关键词召回
python3 scripts/prior_art_search.py cnipa --class G06F9,G06Q10 批任务调度   # 第二轮：带分类号收口
```

第一轮拿回来的每条都带 IPC，脚本还会在 stderr 上给一行 `EPUB_CLASS_HINT: kind=ipc codes=…`。
挑 1～3 个出现最多的分类号，加 `--class` 再查一轮，第二轮的词要比第一轮更贴本案的手段。
写检索记录时以第二轮为主，第一轮当库存：第二轮不够四五条，就从第一轮里捞分类号相同、手段也沾边的补上；
还是少就如实写「检索范围内近邻较少」，不许编条目凑数。

几条要守的：

- **检索词拆成 2～8 个有检索意义的语义块**——专业术语、名词短语、名动组合，空格分开，一次全给脚本，
  它在同一个浏览器里逐个查再按公开号合并。**别把一整句没有空格的长中文当唯一参数**，
  公布站会当整句 AND 处理，极容易 0 条。也别拿「系统」「方法」「智能」这种泛词单独当一个检索单位。
- **链接照抄结果里的 `link`**（`epub.cnipa.gov.cn/patent/…`），不要换成 Google Patents 的地址。
- **有 `abstract` 的条目，必须读懂摘要再写它做了什么**，不能看标题猜。读到摘要按「只读摘要」记，
  要写「它未做 X」得另外打开全文——三档怎么标见 [交底书模板](disclosure-template.md)。
  写进交底书时用自己的话概括，别整段粘官方摘要。
- 这条路要本机 Chrome/Edge 加 playwright。装不上、或站点打不开，就按下面「一个入口都打不开时」处理，
  写「该入口不可用」，不写「未检索到」。0 条命中是检索结论，可以写；打不开不是。

`prior_art_search.py` 的三条脾气：`patents` 和 `get` 走 Google，国内直连网络打不开时它会明说「入口不可用」并以退出码 2 结束，这时按第 4 条继续，不要重试；Google 对同一出口 IP 两分钟内 6 次请求就会拦约 20 分钟，脚本已自动限速，一次多给几个查询式比多跑几次省；被拦后不要重试，先用别的入口。`papers` 和 `code` 走的 OpenAlex、arXiv、GitHub 国内一般能直连。

**入口不可达不是检索结论。** 任何入口失败都不得写成「未检索到」「未发现现有技术」，只能写成「该入口不可用」，并把当时想发的查询式记进未覆盖范围。

### 全文怎么拿

在拿到可读全文之前，文献停留在 `需要取得全文`，不得用摘要下新颖性或创造性结论。取全文按这个顺序：

1. `python3 scripts/prior_art_search.py get <公开号> --out <案件目录>/对比文件/<公开号>.md`：直接得到摘要、权利要求和说明书正文（CN 号默认取中文原文，`--lang en` 取英文机器翻译）。输出里说明书不到 500 字时它会提醒，那多半是页面没给全文，改走 PDF。
2. 用宿主自带的抓取打开专利页或 PDF 地址（`patents` 结果里带 PDF 地址；Espacenet、公布公告也能下 PDF）。
3. 拿到 PDF 之后要确认它真有正文可读。两种情况算没拿到：扫描件（几乎抽不出字），以及没有文字层（抽出来是 `/uni0000004b`、`(cid:113)` 这类字体内部编号，不是文字）。`scripts/pdf_to_text.py` 会把这两种都报出来，报了就按没拿到全文处理——那些字符不得当作原文引用，更不得据此写「未公开该特征」，改从网页版复制原文或另找一份带文字层的 PDF。
4. 都拿不到：该文献留在 `需要取得全文`，检索记录里写清公开号和手动入口（Google Patents 页面、Espacenet、公布公告），交付物里注明结论未经全文核对。

### 一个入口都打不开时

不停下来等，也不放弃检索，把任务做完：

1. 检索记录写明「本轮未能联网检索」和原因（探测结果全不通、被反爬拦、被限流）。
2. 新颖性、创造性按 [模拟审查](examiner-simulation.md) 的 `文件内审模式` 处理：只列待检索假设，不下结论；授权七道门里对应的门标 `BLOCKED`，交付物里如实写「未经检索」，不写「可提交」。
3. 报告末尾附一份**检索式清单**：按上文检索设计拆好的中英文查询式、建议去哪个库查（入口名称与网址）、要带回什么（公开号、公开日、相关段落或全文）。用户有条件时照单子自己查。
4. 用户之后把找到的文献放进案件目录，说一句「补充检索：<文件或文件夹>」，就按正常流程做逐特征对照，并在检索记录里注明该条由用户在哪天取得；只带回摘要或结果页片段的，标 `未取得全文`，按上文处理。

## 现有技术判断

- 对最接近文献做逐特征对照：已公开、部分公开、未公开、表述不清，并标明原文位置。
- 检索页面给的片段、标题和机器摘要只用来决定要不要读全文，不能单独支撑关键特征映射。作新颖性或创造性结论前，读相关实施方式全文、权利要求、上下文和附图，并按 [权项与证据矩阵](claim-evidence-matrix.md) 标明 `明文记载`、`毫无疑义确定`、`未记载` 或 `记载不清`。
- 分开评价单篇文献的新颖性风险和多篇组合的创造性风险。
- 单篇文献的新颖性判断不得用多篇拼接。创造性评价按“最接近现有技术 → 区别特征及其技术效果 → 实际解决的技术问题 → 现有技术是否给出技术启示”展开，实际技术问题不得包含区别手段本身或对其暗示。
- 说明审查员为什么可能或不可能组合这些文献，包括技术领域、要解决的问题、技术启示、相容性和预期效果。声称公知常识时，尽量寻找教科书、技术词典、标准或能够证明其普遍性的证据。
- 使用 [区别特征—创造性矩阵](claim-evidence-matrix.md) 固化结论，功能上相互支持、共同产生效果的特征按组合评价，避免被人为割裂。
- 区分事实、推断和未核实项。没有读到全文时，不对细节作确定结论。
- 授权前景采用条件式结论，不给脱离检索范围和不确定性的裸百分比。
- 检索总结只写成“截至某日，在所列渠道和查询范围内未发现……”或“已发现……”。不得写“无人做过”“不存在现有技术”“已经检索干净”。

## 全文下载与归档

- 用户要求“全文”时，必须取得可打开、可阅读的 PDF 原文；只有摘要、元数据或下载链接不算完成。
- PDF 用真实专利名或论文名命名；文件名过长时作有意义的截断，不用无含义编号代替。
- 按本案技术分类整理并跨类去重，目录层级以一眼能浏览最终 PDF 为准。
- 下载后抽查首页、关键页、页数和可搜索性；损坏、验证码页、HTML 伪装 PDF 或缺页文件应重新获取或明确标记失败。
- 只有用户本次明确要求清理 ZIP、临时文件或重复件时才清理。先核对最终 PDF 完整，再移入废纸篓等可恢复位置；不得把“只留 PDF”泛化到其他案件目录。
- 若需沉淀检索 SOP，只写通用入口、查询方法、下载、备用入口、分类去重和清理步骤，不绑定单次目录或冗长背景。

# 技术交底书模板

用于用户要技术交底书的时候：新案写完申请文件后再出一份，或者用户只要交底书。改稿、评审和答复不套用本文件。

交底书是写给代理人看的。他不认识这个项目，读完就要能自己写出权利要求，还要知道哪些地方得回头问发明人。所以两件事缺一不可：方案写厚到本领域的人照着能做出来；每条机制标清楚是材料里本来就有的，还是我们替他补的。只写厚不标来源，代理人会把补写的当成已实现的写进权利要求；只标来源不写厚，交出去就是一张内部核对单。篇幅不设上限也不靠注水，第三章通常最长。

## 章节

固定七个部分，顺序不变，标题可按用户单位的模板微调：

注意事项 / 一、背景与现有技术（1.1 现有技术、1.2 现有技术的缺点）/ 二、要解决的技术问题 / 三、技术方案详述（3.1 背景、3.2 系统框图、3.3 模块功能、3.4 系统流程、3.4.1 符号与公式、3.5 关键技术参数）/ 四、与现有技术相比的优点 / 五、技术关键点和欲保护点 / 六、其它（实施例、技术效果、参数示例）/ 附：证据状态。

开头写案件名称、技术联系人（姓名、电话、邮箱，没有就留空待填）、专利类型（发明）。「注意事项」是给发明人看的三句话：交底书要让代理人看懂，背景技术和技术方案要全、要清楚；公开程度以本领域普通技术人员不用创造性劳动就能实施为准；代理人来问时认真回答、及时补材料。

## 一、背景与现有技术

1.1 按技术方向分类列现有技术，不按检索先后排。每条写：文献号或标识、申请人或来源机构、它的技术方案、应用场景、局限性、可打开的公开源 URL。URL 必填，写之前实际打开确认它和文献号对得上；打不开就不写这一条，更不能编。开头另起一段写检索说明：查了哪个库、用了哪些检索词、有没有按分类号限定，只写实际做过的事——没做分类号检索就不写「在某分类号下检索」，只看标题没打开的列出文献号说明尚未读。过程按 [检索轨迹台账](search-trail.md) 单独记，这里只放结论。

每条的「局限性」必须对得上我们真读过的原文，并注明读到什么程度：`读过全文`、`只读摘要`、`未取得全文`。三种都能写，但结论强度不一样——只读摘要时只能写「摘要未见 X」，不能写「它未做 X」。凭标题猜文献在做什么是这一章最容易出的错，错了会一路错到第二章和第五章：实测过一份交底书，五篇文献里两篇的区别写反了，偏偏那两篇离本案最近。

1.2 分点写现有技术的缺点，和 1.1 各条的局限性对得上，每条能指出是哪一条现有技术的缺点。申请人自己旧系统的毛病不算现有技术的缺点，要写就另起一段说明这是申请人现状。

## 二、要解决的技术问题

对着 1.2 逐条写本发明怎么解决。这一章短，是第三章的引子，不展开技术细节。一个缺点对一个问题，对不上的删掉——「缺点 → 问题 → 方案 → 保护点」这条线断一环，代理人就写不出创造性论述。

## 三、技术方案详述

### 3.1 背景

固定三小段，不另开小节：

1. 场景与参与者。用案件名称里的领域对象称呼干活的主体，别只写「系统」「模块」。谁在什么环境里、和谁配合、处理什么，一段说清。
2. 标题里那个对象怎么进入系统：怎么被配置、被选中、被调度、被启动。只写材料里有的机制；材料没写就说材料未涉及，别把别的案子的配置方式套上来。
3. 高频术语的场景定义。后面反复出现的领域词各用一句人话定义，必要时补一句怎么判定、怎么记录。定义过的词全文同名。

### 3.2 系统框图

用 mermaid 围栏画（`flowchart TB` 或 `LR`，层次多的用 `subgraph` 分层）。节点名用标题里的领域对象和场景短词，不放公司名、产品名、内部代号，也别把实现字段堆进标签；图复杂就拆几张。不许为了看着通用把标题对象换成更空的上位词：标题写「资源画像」，框图就写资源画像，不写「节点数据」。

交付前按 [撰写与评审规范](drafting-and-review.md)「实施例与附图」一节跑 `scripts/mermaid_render.py` 出 PNG 并嵌进 DOCX。

### 3.3 模块功能

按 3.2 框图的节点，一个节点一项，不把几个节点揉成一条。每项写两件事：这个模块在整个方案里干什么，它和上下游怎么连（谁给它、它给谁、有没有回路）。不写输入输出字段清单，那是接口文档，专利不看这个。模块名、执行主体、交付物名称和 3.1、3.2 用同一套词。

### 3.4 系统流程

流程图同样写 mermaid 围栏，走同一条渲染链。**步骤号要写进能看见的标签**：`S1["S1 采集节点指标"]`，判断节点写 `S5{"S5 是否达阈"}`；写成 `S1[采集节点指标]` 的话序号出不到图上，正文说的「S1」就对不上图。

正文按 S1—Sn 逐项对应着写，图上有几步正文就有几段。不许几步合成一段还不点序号——代理人正是拿这一节去排权利要求的步骤，合并一次就少一个步骤特征。步骤里要让标题那个领域对象真的在做事，不能它只在 3.1 露一面。涉及打分、约束、阈值或其他形式化变量时，设 3.4.1 集中写符号和公式。

### 3.4.1 符号与公式

先给符号表（符号、含义、下标含义、量纲或取值范围），再写公式，再写文字解释。式子里的每个符号都要在表里；同一个字母不能在两处指不同的东西。

每个公式标来源，按 [权项与证据矩阵](claim-evidence-matrix.md) 的「公式与算式来源」一节记：材料转录的写清出处到文件加函数名或段落，本技能补写的明确标出来并给一个能代入的数值例。材料里已有的式子照转，不许为了形式好看改写。公式统一写成 `\(...\)` / `\[...\]` 或 `$...$` / `$$...$$` 一种，`scripts/md_to_docx.py` 会转成 Word 里能编辑的公式。

### 3.5 关键技术参数

阈值、系数、窗口大小这类参数列表：符号、含义、取值范围或本例取值。符号列和 3.4.1 逐字同形。

参数的来源比参数本身重要。材料里有的写出处；我们定的写「示例值」，不写「建议范围」——代理人会把「建议范围」当实测经验值写进从属权利要求。实测踩过一份交底书列了九个参数范围，一个都追不到材料。

## 四、与现有技术相比的优点

先一段总论，再分点，用语和 3.1 的场景词一致；技术细节引第三章。每条优点要能说出它由哪个区别特征产生：有实测或仿真数据的写数据并写明什么条件下得到的，只能从机制推出的把因果链写完整、写明是机制推导。既没数据也推不出来的效果删掉——留着代理人会拿它当创造性论据，答复审查意见时反而站不住。

## 五、技术关键点和欲保护点

每条必须是可实施的机制：对什么输入、怎么判定或怎么控制、得到什么输出。详细内容引第三章的小节号。不许写成「有三个××」这种角色枚举，也不许只把标题对象的名字复述一遍——这两种看着像保护点，代理人拿去写权利要求会发现里面没有技术手段。

每条要能对到 [权项与证据矩阵](claim-evidence-matrix.md) 的一行，并在末尾注明证据状态。核心保护点用了「拟议待验证」的机制就明写出来，代理人据此判断它能不能进独立权利要求。可以在末尾说明哪几条打算做核心保护点、哪几条是从属特征。

## 六、其它

实施例写 2–3 个有名字的实例，名字和 3.1、3.2 一样。每个写清职责、能调用什么能力（工具或资料范围）、交付物、和别的实例怎么互相依赖。至少覆盖主路径加一条第三章已经写过的分支（变更、中断、冲突、限频、降级都行，以本案实际有的为准）。实施例是把方案讲成能想象出来的故事，不是 3.4 的缩写。数值可以是假设的，但每个数都要能当场复算：改了窗口大小，用它算出来的中间值一起改。

技术效果按第四章的要求写。参数设置示例单列一段，注明「不作为权利要求限制」，数值和 3.5 对得上。

## 术语与标题贯穿

全文写完做一遍话题错位检测，做法见 [撰写与评审规范](drafting-and-review.md) 的「表达方式」一节，1.1 到第六章和图里的标签一起换。

标题里的领域实词（去掉「一种」「基于」「方法及系统」这些套话之后剩下的）要在 3.2 框图、3.4 流程、第六章实施例里都出现，指的还得是同一个执行主体。只在 3.1 出现一次，或中途换成更空的上位词，都要改。

## 脱敏

公司名、产品名、内部代号删掉或写成「某系统」；不宜公开的精确数值写成范围或示例；具体业务分类写成分类 A、分类 B。但脱敏不是往上位概括：标题里的领域对象、实施例里的角色名和交付物类型都要具体，只去掉真实主体名。把「数字员工」脱敏成「岗位集群」，代理人就看不出要保护什么了。

## 交付正文里不写的东西

自检清单不写成交底书的一章，检查是我们自己做的；技能仓库名、示例目录路径、「教学示例」「虚构案例」这类元信息不出现；检索评分、红队理由、待办、修改策略这些内部痕迹不带出去。正文止于第六章和证据状态那一节。

例外是「本输出为撰写辅助，不构成法律意见，不保证授权，不代为提交」这句，对外交付必须有；放交付回复里或文末单独一行都行，一个案子前后一致。

## 附：证据状态

这一节是我们和只写交底书的工具最大的差别，不能省。把第三章的每条机制、3.5 的每个参数、第四章的每个效果各列一行，标上 [权项与证据矩阵](claim-evidence-matrix.md) 开头那六种状态之一：直接证据、必然可推出、参考实现支持、发明人确认、拟议待验证、无依据。

```markdown
| 内容 | 位置 | 证据状态 | 出处或说明 |
|---|---|---|---|
```

三条硬要求：

1. 材料里没有、由本技能补写的机制必须标出来，这是这一节存在的理由。实测过一份 3.4 万字的交底书，30 项事实性陈述里 13 项是补写的、一处没标，其中 4 项进了第五章保护点——代理人照着写，核心特征就是一个从没实现过、也没人确认过的算法。
2. `无依据` 的内容不写进交底书。写不进去就删，或者先补到能标成别的状态。
3. 参数范围和技术效果单独再看一遍，这两处最容易凭空生成。

代理人看完就知道哪些能直接写进权利要求，哪些得回头问发明人。第五章保护点后面标的状态要和这一节一致。
